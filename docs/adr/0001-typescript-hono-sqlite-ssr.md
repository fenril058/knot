# 0001: TypeScript + Hono + SQLite の単一プロセスで作る

- 状態: 承認済み
- 決定日: 2026-07-10（記録日: 2026-08-02）

閲覧は SSR、編集画面だけ CodeMirror 6 を載せる構成とし、サーバは Hono、ストレージは `node:sqlite` にした。
検討した候補（Go、TypeScript）のうち、Cosense 記法のパーサ資産（`@progfay/scrapbox-parser`）をそのまま使えて、かつサーバとエディタを単一言語で書けるのが TypeScript だけだったことが決め手である。
将来 Cloudflare Workers + D1 でも動かせるよう、ストレージ層は差し替え可能な境界として保つ。

## 却下した案

**Go 単一バイナリ**。
配布は最も単純だが、Scrapbox 記法パーサを自作することになり、互換性の最難関を自前で背負う。
加えて Workers への移行路が事実上閉じるため、要件と矛盾する。

CRDT ファーストを採らなかった理由は書き込みモデルの決定なので [0002](0002-line-ops-as-canonical-write-form.md) に記す。

## 明文化されていない制約

- 想定利用者は 2〜5 人。
- 運用費は月 1000 円以内（自宅 PC + Cloudflare Tunnel、または格安 VPS）。
- ネイティブ依存のビルド問題と依存パッケージの寿命リスクを避けるため、SQLite とパスワードハッシュ（scrypt）はランタイム内蔵機能を使う。
  `node:sqlite` の API が安定途上である点は残るリスクとして受け入れ、問題が出た場合は better-sqlite3 へ差し替える。
  この差し替えが `src/storage/` の内側で完結することが、ここでの設計上の条件である。

## Cloudflare Workers / D1 へ移す場合に作り直す範囲

`node:sqlite` と scrypt への依存は storage と auth の内側に閉じてある。
FTS5 の trigram が D1 で使えない場合に備え、検索は storage interface の 1 メソッドとして抽象化してある。
ここまでは差し替えで済む。

差し替えでは済まないものが 2 つある。

- **D1 では複数ページの原子的更新を前提にできない。** リネームに伴うリンク書き換えは「冪等なジョブとして記録し、失敗したページを再実行できる」方式へ作り直す必要がある。
- **Node 固有の I/O を持つハンドラはそのまま動かない。** Hono のルーティング構造は流用できるが、添付の保存と配信は `node:fs/promises` を直接呼んでおり（`src/server/routes/files.ts`）、静的ファイル配信も `@hono/node-server/serve-static` に依存している。R2 へ移すならこれらの依存境界を切り直す。

実際に移行方式を決めるときは、その時点で別の ADR を書く。ここにあるのは見積もりのための制約である。

## 受け入れた残余リスク

- **`@progfay/scrapbox-parser` は実質単独メンテである。** 依存ゼロの純粋なパーサで対象記法も安定しているため採用したが、バージョン固定とゴールデンテストを受け入れ条件とし、必要なら fork を維持することまで織り込んでいる。
  現在 `10.1.1` に固定してあるのはこの条件のためで、無条件に上げてよい依存ではない。自前実装への置き換えは #17。
- **添付アップロードの multipart はボディ全体をメモリに載せて解析する。** `Content-Length` が上限を超えていれば解析前に 413 を返すが、ヘッダが無い場合と偽装された場合は解析後のサイズ検査でしか弾けない。
  ログイン必須のクローズドな wiki であることを前提に、この残余リスクを受け入れている。公開モードを足すならストリーミング解析が要る。
