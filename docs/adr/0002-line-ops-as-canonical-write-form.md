# 0002: 行操作とページ version を書き込みの正準形式にする

- 状態: 承認済み
- 決定日: 2026-07-10（記録日: 2026-08-02）

ページ本文の変更は、コミットログ上つねに `insert` / `update` / `delete` の 3 種の行操作として表現する。
コミットは `{commitId, baseVersion, ops[]}` を単位とし、単一トランザクションで適用して version を 1 増やす。
`baseVersion` が現在の `pages.version` と一致することは適用の必要条件であり、十分条件ではない（後述）。
version が競合した場合は 409 で返し、クライアントは 3-way リベースで操作列を作り直して再送する。

ただしインポートは実行経路としては `applyOps` を通らない。
Cosense 由来の行 ID と時刻を保持するために行を直接書き、等価な操作列を `commits` に記録する。
「行操作が正準形式である」はコミットログの表現についての主張であって、すべての実行経路が同じ関数を通るという主張ではない。

ページ全文を置き換える API を正準形式にしなかったのは、他者が編集した行を旧テキストで上書きしてしまうためである。

## 却下した案

**CRDT（Yjs）ファースト**。
リアルタイム共同編集を最初から得られるが、真のデータが CRDT の内部表現になり、SQLite の行を直接読める透明性を失う。
2〜5 人の利用では衝突がまれで、複雑さに見合わない。

CRDT なしでも Cosense 相当のリアルタイム共同編集に到達できる根拠は、Cosense 自体が CRDT ではなく行単位の操作をサーバで直列化する方式であることによる。

## 帰結

- **リアルタイム化の拡張点は `rebase` である。** `src/core/rebase.ts` は 3 つの行スナップショット（最後に同期した状態、手元の状態、最新状態）だけを入力とする純関数で、コミット列を必要としない。
  リアルタイム化は、この関数を 409 契機ではなく WebSocket の受信契機で回すことに相当する。
  「作り直しなしでリアルタイム化できる」という主張の実体はこの関数であり、テストごと消してはならない。
- **409 応答は最新の version と全行を返さなければならない。** リベースの入力が 409 応答だけで揃うことが、API とリベースの整合条件である。
- **409 になる競合は 2 種類ある。** `baseVersion` が現在の version と食い違う場合と、適用結果のタイトルが同じプロジェクトの生存ページと衝突する場合である。
  後者は `baseVersion` が一致していても起きるので、version の一致だけを適用条件と考えてはならない。
- **競合は 409、クライアント不正は 400。** 存在しない行 ID への `update` / `delete`、`after` の指す行の不在、`insert` の行 ID 重複、空の ops 配列に加えて、未知のページや削除済みページへのコミットも 400 でロールバックする。
- **冪等性キーは `commitId` で、`ops_hash` はその検証に使う。** 再送はまず `commits.id` を引き、見つかれば `ops_hash`（正規化した `{pageId, baseVersion, ops}` のハッシュ）を照合する。
  一致すれば最初に適用したときの version を成功応答で返し、一致しなければ「同じ ID で内容が違う」として 400 で拒否する。
  DB に持つのでプロセス再起動後も保たれる。
  リベースで ops が変わったコミットは新しい `commitId` を発行する。
- **ページ本文の変更はすべて `commits` に残る。** ページ削除も「全行の delete」のコミットとして記録し、`pages` 行と `commits` は保持する。
  一方、ピン留めと閲覧記録は本文の変更ではないので直接更新し、`commits` には入らない。
- **インポートのトランザクションはページ単位である。** 巨大なエクスポートを単一トランザクションにしない判断であり、途中で失敗するとそこまでのページが取り込まれた状態で止まる。
  部分的に取り込まれた状態は正常な結果であって、破損ではない。再実行するときは既存ページの扱い（スキップか上書きか）を意識する必要がある。
