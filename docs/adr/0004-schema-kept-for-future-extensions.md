# 0004: v1 で読まないスキーマと抽象化を将来拡張のために残す

- 状態: 承認済み
- 決定日: 2026-07-10（記録日: 2026-08-02）

`title_history` と `page_visits` は v1 では書くだけで、読む UI を持たない。
storage は SQLite 実装に直結させず、差し替え可能な interface として保つ。
どちらも v1 単体では過剰だが、後から足すと既存データが無い状態から始まるため、最初から書いておく。

未使用に見えても消してはならない。
消した時点で、それ以前の期間について機能を提供できなくなる。

## 旧タイトルからのリダイレクト

存在しないタイトルへのアクセスを、タイトル変更前にその名を持っていたページへ転送する機能のためのものである。

素朴に「タイトル変更の履歴」を引くだけでは成立しない。
タイトル行の編集は逐次保存されるので、「カレー」を「curry」へ変える途中の「カレ」「カ」「c」「cu」といった一時タイトルが履歴に残り、「カ」へのアクセスが curry へ転送されてしまう。
Cosense がアクセス履歴方式を採っているのはこの理由による。

knot の `title_history` は有効期間（`started`、`ended`）を持つので、「一定時間以上そのページのタイトルであり続けたタイトル」だけを対象にする方針を第一候補とする。
編集途中の一時タイトルは数秒しか存続しないため、この条件で外れる。

精度が足りなければ、Cosense と同じアクセス履歴方式へ切り替えられる。
テロメアのために v1 から記録している `page_visits` と `title_history` を突き合わせれば、「そのタイトルであった期間に実際に閲覧されたことのあるタイトル」だけを対象にできる。

どちらの方式でも、差し込み点は v1 の 404 ハンドラ（新規作成を促す画面）ひとつである。

## Cloudflare Workers / D1 へ移す場合に作り直す範囲

server は Hono なのでハンドラはそのまま動く。
storage の SQLite 実装を D1 実装に差し替え、添付ファイルを R2 に置く実装を足す。

**D1 では複数ページの原子的更新を前提にできない。**
そのため、リネームに伴うリンク書き換えは「冪等なジョブとして記録し、失敗したページを再実行できる」方式に置き換える必要がある。
これは差し替えでは済まない作り直しなので、移行を検討する際の見積もりに入れる。

FTS5 の trigram が D1 で使えない場合に備え、検索は storage interface の 1 メソッドとして抽象化してある。
`node:sqlite` と scrypt への依存も storage と auth の内側に閉じてある。
