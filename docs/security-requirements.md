# 実装の安全要件

knot を変更するときに維持する要件を示します。
コードから読み取れるが、壊したことに気づきにくいものを集めています。

脆弱性の報告先はこの文書ではなく [SECURITY.md](../SECURITY.md) です。
ファイル名が `security.md` でないのは、GitHub が `.github/`・リポジトリルート・`docs/` にある `SECURITY.md` を（大文字小文字を区別せず）リポジトリのセキュリティポリシーとして公開するためです。
以前この文書は `docs/security.md` にあり、報告者向けのポリシーとして表示されていました。

現在のアクセス境界を選んだ理由は [ADR 0005](adr/0005-closed-wiki-access-boundary.md) を参照してください。

## 前提と対象外

**ログイン済みの利用者は信頼します。**
v1 はログインした利用者全員が全プロジェクトを読み書きできるクローズドな wiki です。
利用者どうしを隔離する仕組みはありません。

この前提の上に、以下の設計が成り立っています。

- レート制限はログイン試行にしか掛かっていない
- 添付ファイルの配信はプロジェクトの所属を検査しない
- アップロード処理がボディ全体をメモリに載せる

公開閲覧やプロジェクト単位の権限を追加するときは、認可規則だけでなく、これら 3 つの前提をすべて再評価してください。
どれも「ログイン済み利用者しかいない」ことに依存しています。

## 認証と認可

### 認証を要求する範囲

`classifyRequest`（`src/server/app.ts`）が経路を 3 つに分類します。

| 分類 | 対象 | 未認証のとき |
| --- | --- | --- |
| `public` | `/login`（メソッドを問わない。登録済みなのは `GET` だけ）、`POST /api/knot/session`、`/assets/*` | 通す |
| `api` | `/api/*`、`/files/*` | 401 |
| `html` | それ以外 | `/login?next=...` へ 302 |

`api` はセッション cookie と personal access token（PAT）の両方を受け付けます。
`html` はセッション cookie だけを受け付けます。
PAT は `x-personal-access-token` ヘッダで渡し、`api` 分類でしか読み取りません。

### 認可

ログインさえしていれば、すべてのプロジェクトを読み書きできます。
プロジェクト単位・ページ単位の権限判定はありません。

`isAdmin` はユーザーレコードとログイン応答に存在しますが、**ルートの認可判定には一切使われていません**。
このフラグを見て権限差があると考えないでください。

添付ファイルの配信（`src/server/routes/files.ts` の `serveFile`）は ULID の形式だけを検査し、その添付がどのプロジェクトに属するかを見ません。
ID を知っているログイン利用者は誰でも取得できます。
全員が全プロジェクトを読める現状では問題になりませんが、権限を分ける変更を入れるときはここが穴になります。

### セッション

セッション ID は `randomBytes(16)` で生成します。
`connect.sid` cookie に保存し、`HttpOnly`、`SameSite=Lax`、`Secure` を付けます。

`secureCookie` の既定値 `"auto"` は、起動時に `--hostname` から真偽値へ解決されます（`src/cli/commands.ts`）。
アプリ側は `false` と明示されたときだけ `Secure` を外します。
リバースプロキシ構成での設定は [運用ガイド](ops.md#3-リバースプロキシ) を参照してください。

有効期限は既定で 30 日です。
残りが 24 時間分減るたびに延長し、cookie を再送します。

## CSRF 境界

`/api/knot/*` への `POST`・`PUT`・`DELETE` は `X-Knot-Client` ヘッダを要求します。
**認証方式を問いません。**
この検査は認証ミドルウェアより前に登録されているため、PAT を使うクライアントも付ける必要があります（`src/cli/sync/client.ts` が実例です）。

`SameSite=Lax` と、クロスオリジンの単純なフォーム送信では付けられないヘッダの組み合わせを CSRF 境界とします。

**ページ・プロジェクト・添付・セッションを変更する `POST`・`PUT`・`DELETE` は `/api/knot/` 配下に置いてください。**
ヘッダ検査はパスの前置詞で効いています。
この配下の外に unsafe method のルートを 1 本足すと、CSRF 境界がエラーを出さずに漏れます。
現在 `src/server/routes/write.ts` と `files.ts` の unsafe method のルートはすべてこの配下にあります。

「状態を変える要求がすべてこの配下にある」わけではありません。
ページ表示の `GET /:project/:title` は訪問記録を更新し、認証ミドルウェアは条件を満たせばセッションを延長します。
CSRF 境界が守っているのは、利用者が意図しない**内容の変更**です。

## 秘密情報の保管

**パスワード**は scrypt（N=16384、r=8、p=1、salt 16 バイト、鍵長 32 バイト）でハッシュ化し、`timingSafeEqual` で比較します。

保存文字列に埋め込まれたパラメータは、検証して使うのではなく固定値と一致するかだけを見て、違えば照合を失敗させます。
DB 内の値をそのまま `scryptSync` に渡すと、巨大な `N` を仕込まれてイベントループを止められるためです。
パラメータを可変にする形へ書き換えないでください。

**PAT** は `knot_` + `randomBytes(24)` の base64url で発行し、SHA-256 ハッシュだけを保存します。
平文はサーバに残りません。
ストレッチングなしの単純ハッシュで足りるのは、トークンが 24 バイトの CSPRNG 出力で、辞書攻撃や総当たりの対象にならないためです。
低エントロピーの値をこの経路に流さないでください。

## HTML と外部コンテンツ

利用者の入力を HTML に変換するときは、テキストノードと HTML 属性値をエスケープします。
外部のリンク、画像、動画、音声は `http:` と `https:` だけを扱います（`src/core/media.ts`）。
サイト内のページリンクと `/files/*` の添付 URL は別経路で扱います。

**iframe は生成しません。**
`allowedFrameHosts` は CSP の `frame-src` にしか反映されません。
埋め込みを実装するときは、ホストの検証を CSP 任せにせず生成側にも置いてください。

Content Security Policy は、エスケープや URL 検証が破られた場合の被害を抑える追加の防御です。
CSP を出力時の安全化の代わりにしません。

現在の CSP は `default-src 'self'` を基点に、`img-src`・`media-src` へ設定の許可ホストを、`frame-src` へ `allowedFrameHosts`（空なら `'none'`）を足したものです。
編集画面の応答では `style-src 'self' 'nonce-...'` を追加します。
この nonce は SSR の出力ではなく、CodeMirror がクライアント側で生成する style のためのものです。

`frame-ancestors` と `X-Frame-Options` は**現在ありません**。
これは既知の不足です。

`SameSite=Lax` は、対応ブラウザで**クロスサイト**の iframe にセッション cookie が送られることを防ぎます。
しかし `SameSite` の単位は origin ではなく site（登録可能ドメイン）です。
ポートが違うだけの別 origin、同じ登録可能ドメイン配下の別ホストからの埋め込みには cookie が送られ、認証済みの編集 UI がそのまま描画されます。
実測でも、別ポートから認証済みページの iframe 埋め込みが成功しています。

したがって `SameSite=Lax` はクリックジャッキングの完全な防御ではありません。
knot を他所へ埋め込む要件が無いなら `frame-ancestors 'none'` を追加してください。
ログイン画面自体も枠に嵌められるため、資格情報入力に対する UI 偽装の余地も残ります。

すべての応答に `X-Content-Type-Options: nosniff` を付けます。

## 添付ファイル

アップロードは `maxUploadBytes`（既定 10 MiB）を超えると拒否します。
multipart の解析前に `Content-Length` が `maxUploadBytes + 64 KiB` を超える要求を弾き（64 KiB は multipart のオーバーヘッド分）、解析後に `File.size` と実バイト長を `maxUploadBytes` と比較します。

ただしこれは**保存を拒否する条件であって、メモリ消費の上限ではありません**。
`parseBody()` は multipart 全体を先にメモリへ読み、その後 `file.arrayBuffer()` でもバイト列を作るため、ピーク時にはボディ 1 個分を超えます。
`Content-Length` を付けない chunked request は事前検査を素通りし、上限なしに読み込まれます。

body limit は multipart に限らず**どの経路にもありません**。
未認証で叩けるログイン API も、JSON 全体を読んでからレート制限に到達します。
ログイン済み利用者を信頼する前提で受け入れている制約ですが、ログイン API はその前提の外にあります。
公開アップロードを追加する前に、ストリーミング処理とリソース制限を設計してください。

マジックバイト検査は `MAGIC` に定義した形式（png、jpeg、gif、webp、mp4、webm、mpeg、ogg、wav）にだけ掛かります。
そこにない Content-Type は無検査で保存されます。

この検査は先頭数バイトの署名照合であって、形式の完全な検証ではありません。
ファイル全体が妥当であることも、polyglot でないことも保証しません。

無検査で通る形式があっても安全なのは、**配信側で塞いでいるため**です。
`INLINE_TYPES` に列挙した形式だけをインラインで配信し、それ以外には `Content-Disposition: attachment` を付けます。
HTML や SVG が最上位で描画されないのはこの一段だけに依存しています。

**`INLINE_TYPES` と `MAGIC` の集合は一致させてください。**
現在はどちらも同じ 9 形式です。
`INLINE_TYPES` にだけ形式を足すと、申告された Content-Type を無検査のままインラインで配信することになり、配信側の防御が抜けます。

## レート制限

`RateLimiter` はログイン試行にだけ掛かります。
接続元 IP とユーザー名の組で 10 分あたり 10 回です。

制限に到達するのは、JSON の解析と `name`・`password` の型検査を通過した要求だけです。
壊れた JSON や型の違う body はレート制限を数えずに 400 を返すため、この経路は無制限に叩けます。
状態はプロセスごとに持ち、再起動で消え、複数プロセス間では共有されません。

書き込み、アップロード、検索、エクスポートに制限はありません。
「前提と対象外」に書いたとおり、ログイン済み利用者を信頼する前提の帰結です。

接続元 IP は TCP のソースアドレスから取ります（`clientIp`）。
`X-Forwarded-For` は読みません。
リバースプロキシ配下での帰結は [運用ガイド](ops.md#3-リバースプロキシ) を参照してください。

## 回帰テスト

セキュリティヘッダの存在だけでなく、悪意ある入力が実行可能な HTML にならないことをテストします。
次の項目を回帰テストの対象に保ちます。

- 経路の分類と認証範囲、PAT 認証
- `X-Knot-Client` の要求。**有効な PAT を持つ要求でもヘッダ欠落を拒否すること**（現在この組み合わせを直接検証するテストは無い）
- 外部 URL スキームの制限と、CSP の `frame-src`
- 添付のマジックバイト検査、インライン配信・添付配信の切り分け、**`INLINE_TYPES` と `MAGIC` の集合一致**
- パスワードハッシュの照合（保存パラメータを差し替えた値を拒否すること）

## テストが守っていない不変則

以下はコードのコメントか実装の形でしか存在せず、壊しても現在のテストは失敗しません。
触るときは意図的に確認してください。

- **ログイン後の遷移先は同一オリジンに限る**（`public/login.js`）。
  `next` パラメータを `location.origin` で解決し、origin が一致したときだけ遷移先に使う。
  外部 URL を渡すテストが無い。
- **PAT を載せた要求はリダイレクトを追わない**（`src/cli/sync/client.ts`）。
  `redirect: 'error'` で別 origin への認証ヘッダ転送を防ぐ。
  テストはヘッダとメソッドしか見ていない。
- **CSP nonce は応答ごとに新しく予測不能であること**（`src/server/routes/pages.ts`）。
  テストは base64 の形しか見ないため、固定文字列に置き換えても通る。
- **セッション cookie に `Domain` を付けない**（`src/server/app.ts`）。
  付けると兄弟ホストへ cookie が送られる。
  省略していることを検証するテストが無い。
- **添付の `Content-Disposition` はファイル名を encode する**（`src/server/routes/files.ts`）。
  `encodeURIComponent` がヘッダ注入を防ぐ。
  CR/LF を含むファイル名のテストが無い。
