# knot 設計書

作成日: 2026-07-10
状態: 承認待ち

## 目的

**knot** は、Cosense（旧 Scrapbox）のデータ構造と記法に互換な、セルフホスト可能な OSS の wiki である。

Cosense はサービスとして優れているが、OSS ではないため、サービス終了時にはデータの受け皿を失う。
knot は Cosense のエクスポート JSON を無加工で取り込み、いつでも Cosense 互換 JSON で書き出せる「受け皿」を提供する。
同時に、行単位のデータモデル、ブラケットリンク、関連ページによる自己組織化という Cosense の設計思想を引き継ぐ。

## 要件（確定事項）

ヒアリングで確定した要件は次のとおり。

- 利用者は 2〜5 人。将来リアルタイム共同編集が必要になった場合に、作り直しなしで拡張できる設計にする。
- v1 は単一プロセス + SQLite で動かす。将来 Cloudflare Workers + D1 でも動かせるよう、ストレージ層を差し替え可能にしておく。
- 記法は Scrapbox 記法をそのまま採用する。
- Emacs や Vim などの外部エディタとの同期は v2 で実装する。v1 では、それを可能にする API だけを用意する。
- v1 はログイン必須のクローズドな wiki とする。公開モードは後から足す。
- 運用費は月 1000 円以内。自宅 PC + Cloudflare Tunnel（0 円）または格安 VPS を想定する。
- ライセンスは MIT とする。

## v1 のスコープ

実装するもの:

- 複数プロジェクト（Cosense のプロジェクトに相当する独立した wiki 空間）のホスト
- ページの閲覧（SSR）、編集（CodeMirror 6）、作成、タイトル変更、削除、複製、ピン留め
- Scrapbox 記法のパースとレンダリング
- リンクグラフ（1-hop リンク、2-hop リンク、空リンク、逆リンク）
- テロメア（行ごとの編集の新しさの可視化、未読の強調、行 permalink）
- 日本語対応の全文検索と、インクリメンタルなあいまいタイトル検索
- Cosense エクスポート JSON のインポートと、Cosense 互換 JSON のエクスポート
- Cosense の読み取り API と同一形状の HTTP API
- 行操作コミットによる書き込み API
- 画像などの添付ファイルのアップロード
- パスワードログインとセッション管理
- CLI（サーバ起動、ユーザー管理、インポート、エクスポート、バックアップ、導出データの再構築）

実装しないもの（設計上の拡張点は確保する）:

- リアルタイム共同編集（「将来拡張」の節を参照）
- 外部エディタ同期 CLI（同上）
- public 公開モード
- Cloudflare Workers / D1 バックエンド
- ページ履歴の UI（コミットログ自体は v1 から記録する）
- 旧タイトルからのリダイレクト（材料になる title_history は v1 から記録する）
- 数式の KaTeX レンダリング（v1 ではコード表示で代替する）
- 通知、ストリーム表示

## 採用アプローチと代替案

**案A+（採用）**: TypeScript + Hono + SQLite。閲覧は SSR、編集画面のみ CodeMirror 6 を載せる。
書き込みは最初から「行操作 + ページ version」を正準形式とする。
ここで**正準形式**とは、あらゆる書き込み経路（Web エディタ、全文置換 API、インポート）が最終的に帰着する唯一の表現、という意味である。

代替案とその不採用理由:

- **Go 単一バイナリ**: 配布は最も単純だが、Scrapbox 記法パーサを自作する必要があり、互換性の最難関を自前で背負う。また Cloudflare Workers への移行路が事実上閉じ、確定要件と矛盾する。
- **CRDT（Yjs）ファースト**: リアルタイム共同編集を最初から得られるが、真のデータが CRDT の内部表現になり、SQLite の行を直接読める透明性を失う。2〜5 人の利用では衝突がまれで、複雑さに見合わない。

CRDT を採用しなくても Cosense 相当のリアルタイム共同編集に到達できる根拠は、Cosense 自体が CRDT ではなく行単位の操作をサーバで直列化する方式であることによる。
行操作を正準形式にしておけば、リアルタイム化は「同じ操作を WebSocket で配信する」追加実装に収まる（「将来拡張」の節で詳述する）。

## アーキテクチャ

```
ブラウザ
 ├─ 閲覧: SSR された HTML（Hono/JSX）
 └─ 編集: CodeMirror 6（記法ハイライト、リンク補完、自動保存）
      │ HTTP (JSON)
      ▼
knot サーバ（Node.js LTS + Hono、単一プロセス）
 ├─ render:  scrapbox-parser の AST → HTML
 ├─ core:    コミットエンジン（行操作の適用、version 管理、リンク索引更新）
 ├─ storage: リポジトリ層（interface。v1 実装は node:sqlite）
 └─ 静的アセットと添付ファイルの配信
      │
      ▼
data/
 ├─ knot.db   … SQLite（全データ）
 └─ files/    … 添付ファイル
```

実行時依存は Hono、@progfay/scrapbox-parser、CodeMirror 6 の三つに限定する。
DB アクセスは Node 内蔵の node:sqlite、パスワードハッシュは Node 内蔵の scrypt を使い、ネイティブ依存を持たない。

### ソースレイアウト

```
src/
  core/     行操作、コミットエンジン、行差分、タイトル正規化、リンク抽出
  render/   AST → HTML レンダラ
  storage/  Storage interface、SQLite 実装、マイグレーション
  server/   Hono アプリ、ルーティング、認証、SSR ビュー
  client/   エディタ（CodeMirror 設定、補完、自動保存）
  cli/      knot コマンド
test/
```

core と render は I/O を持たない純粋なモジュールとし、storage と server から独立にテストできるようにする。
将来の Workers 対応で書き換えるのは storage の実装と server の起動部だけ、というのがこの分割の意図である。

## データモデル

### スキーマ

```sql
projects    (id, name UNIQUE, display_name, created, updated)
users       (id, name UNIQUE, display_name, email, password_hash, is_admin, created)
pages       (id, project_id, title, title_lc, version, pinned, deleted, image, created, updated)
lines       (id, page_id, ord, text, created, updated, updated_version, user_id)
commits     (id, page_id, base_version, version, user_id, created, ops, ops_hash,
             UNIQUE(page_id, version))
title_history (page_id, old_title, old_title_lc, started, ended)
page_visits (user_id, page_id, visited, last_seen_version)
links       (project_id, source_page_id, target_title_lc)
attachments (id, project_id, filename, content_type, size, sha256, user_id, created)
sessions    (id, user_id, expires, created)
pages_fts   (FTS5 仮想テーブル、tokenize='trigram')
```

- タイムスタンプはすべて Unix 秒（Cosense と同じ）。
- ID は ULID で発行する。インポート時は Cosense 側の ID をそのまま保持する。
- タイトルの一意性は部分インデックス `UNIQUE(project_id, title_lc) WHERE deleted = 0` で保証する。削除済みページが同タイトルの再作成を妨げないためである。
- `lines.ord` はページ内の行順。コミット適用時に振り直す（v1 は全行の振り直しで足りるが、影響範囲だけ振り直す最適化余地を残す）。
- `commits.ops` は行操作の JSON 配列。追記のみで、v1 では読み取る UI を持たない。
- `pages.image` は**代表画像**（ページ内の最初の画像 URL、なければ空）である。コミット適用時に AST から導出して保存し、ページ一覧のカード、読み取り API の image フィールド、リンク先のプレビューに使う。一覧 API の descriptions（冒頭数行）は lines から都度取得する。
- `title_history` はタイトル変更コミットの適用時に、旧タイトルとその有効期間を追記する。v1 では書くだけで読む UI を持たない。旧タイトルからのリダイレクト（「将来拡張」の節を参照）の材料である。
- `page_visits` はページ閲覧時に、閲覧時刻とそのとき表示した version（`last_seen_version`）を upsert する。テロメアの未読判定は時刻ではなく version の比較（`lines.updated_version > last_seen_version`）で行う。行更新と閲覧が同じ Unix 秒に起きても判定が曖昧にならないためで、`lines.updated_version` には行を最後に変更したコミットの version を持たせる。時刻（Unix 秒）は表示と Cosense 互換のために保持する。page_visits はアクセス履歴方式の旧タイトルリダイレクト（将来拡張）の材料も兼ねる。
- `links` はページ保存のたびに AST から抽出して張り直す導出テーブル。
- links、pages_fts、pages.image は lines から再構築できる導出データである。`knot reindex` コマンドで全導出データを作り直せるようにする。索引の破損対策であると同時に、リンク抽出やレンダリングのロジックを変更したときの再適用手段を兼ねる。
- `pages_fts` はタイトルと全行を連結したテキストを索引する。trigram トークナイザにより日本語の部分一致検索が成立する。ただし trigram は 3 文字未満のクエリでは索引を引けず、エラーではなく 0 件を返す（実測で確認）。日本語は 2 文字の語が多いため、クエリが短い場合は `lines.text` への LIKE 走査にフォールバックする。この分岐は storage の検索メソッドの内側に閉じる。
- マイグレーションは連番 SQL ファイルを起動時に適用する方式とし、適用位置は `PRAGMA user_version` で管理する。

### タイトル正規化

**title_lc** は、タイトルを Unicode NFC 正規化し、小文字化し、空白 (U+0020) を `_` に置換した文字列である。

- リンク解決は title_lc の一致で行う。`[Foo Bar]` と `[foo_bar]` は同じページを指す。
- URL パスもこの規則で解決する（`/:project/Foo_Bar` はタイトル「Foo Bar」のページ）。
- この規則は Cosense の titleLc の観察された挙動（小文字化、空白とアンダースコアの同一視）に合わせた knot 独自の定義であり、Cosense 内部実装との完全一致は保証しない。

### タイトルと URL の対応

- ページ URL は Cosense と同じ `/:project/:title` の形状を保つ。タイトルは percent-encoding して 1 つのパスセグメントに収め、`/` `?` `#` `%` を含むタイトルも往復できるようにする。エンコードと復号は 1 か所に実装し、これらの文字と空白、アンダースコアを含むタイトルの往復テストを置く。
- URL フラグメント（行 permalink の `#行ID`）はサーバに送信されないため、クライアント側で解釈する。タイトル中の `#` は percent-encoding されるので、サーバ側で行 permalink と曖昧にならない。
- プロジェクト名は `[a-z0-9-]` に制限し、`api` `login` `files` `assets` を予約語として使用不可にする。これでページ URL と他のルートが衝突しない。
- percent-encoding された `/`（%2F）をパス正規化で潰すリバースプロキシが存在するため、運用ドキュメントにプロキシの設定例を示す。

### 行操作とコミット

書き込みの正準形式は次の三種の**行操作**である。

```json
{"type": "insert", "id": "<新しい行ID>", "after": "<行ID> | _head", "text": "..."}
{"type": "update", "id": "<行ID>", "text": "..."}
{"type": "delete", "id": "<行ID>"}
```

**コミット**は `{commitId, baseVersion, ops[]}` の単位で適用する。

- `baseVersion` が現在の `pages.version` と一致する場合のみ、ops を配列順に単一トランザクションで適用し、version を 1 増やし、commits に追記する。
- 行順はコミットの逐次適用だけで決まる。コミットはサーバが受理した version 順、コミット内の ops は配列順に適用されるため、同じコミット列からは常に同じ行順が得られる。クライアントが連続して行を挿入するときは、直前に挿入した行をアンカーにして ops を生成し、入力順を保つ。同じ行のあとへの並行挿入は、後に受理されたコミットの行がアンカーの直後に入る。この期待順序はテストで固定する。
- 不一致の場合は 409 と最新のページ状態（version と全行）を返す。クライアントは後述のリベースを行って再送する。
- 存在しない行 ID への update / delete、`after` の指す行の不在（同一コミット内で削除済みの行を指す場合を含む）、insert の行 ID 重複、空の ops 配列は、競合ではなくクライアント不正として 400 で拒否し、コミット全体をロールバックする。
- `commitId` はクライアントが ULID で発行し、commits の主キーとして一意性を保証する。再送の同一性は「正規化した `{pageId, baseVersion, ops}` のハッシュ」（`commits.ops_hash` として保存）で判定し、同一なら最初に適用したときの version を成功応答で返す（冪等。DB に持つためプロセス再起動後も保たれる）。同じ commitId で内容が異なる要求は 400 で拒否する。リベースで ops が変わったコミットは新しい commitId を発行する。
- ページの先頭行はタイトルである（Cosense と同じ）。コミット適用の結果として先頭行のテキストが変わった場合（update に限らず、`_head` への insert や先頭行の delete で先頭行が入れ替わった場合を含む）はタイトル変更として扱い、`pages.title` と `title_lc` を同時に更新する。title_lc の一意制約に反する場合はコミット全体を 409 で拒否する。
- ページの新規作成は「タイトル行 1 行だけの insert を含む最初のコミット」で行う。空のページ行は作らない。
- ページ削除は「全行の delete」のコミットとして記録し、`pages.deleted` を立てる。pages 行と commits は保持する（すべての書き込みが commits に残る、という不変条件）。削除済みページはエクスポートに含めず、閲覧 URL は新規作成を促す画面（404 系統）を返す。削除後に同タイトルのページを作る場合は新しい page_id で始め、コミット履歴はページごとに独立させる。
- コミット適用時に、該当ページの links と pages_fts の索引を更新する。

### リベース

409 を受けたクライアントの再適用は、core の純関数 `rebase(baseSnapshot, localBuffer, latestSnapshot) -> ops'` として仕様化する。
入力は 3 つの行列スナップショット（最後に同期した状態、手元の状態、409 応答が返した最新状態）だけであり、コミット列を必要としない。
つまり 409 応答だけで再送する操作列を計算できることが、API とリベースの整合条件である。

- 3-way で解決する。「最新サーバ状態と自バッファの再差分」だけで ops を作り直す実装は、自分が触っていない行への他者の編集を旧テキストで上書きするため、禁止する。
- 同一行が両者で更新されていた場合は行単位で解決する。「後勝ち」の「後」は**サーバの受理順**である。リベース後の再送は受理順で必ず後になるため、再送されたローカルの内容が先行する更新を置き換える。1 行を衝突の単位とするのは Cosense と同じ粒度である。
- insert の `after` が指す行が最新状態に存在しない場合は、baseSnapshot でその行の直前にあった生存行に付け替える（生存行がなければ `_head`）。挿入内容そのものは失わない。
- **収束**とは、すべてのクライアントが最終的にサーバと同じページ状態へ到達することを指す。競合した双方の変更が両方残ることまでは意味しない。
- 将来のリアルタイム共同編集は、このリベースを 409 契機ではなく WebSocket の受信契機で回すことに相当する。この関数が v1 で仕様とテスト込みで存在することが、「作り直しなしでリアルタイム化できる」という主張の実体である。

## Cosense 互換性

### 記法

パーサは @progfay/scrapbox-parser（MIT）をそのまま使う。
対応する記法はパーサが受理する全種で、主なものは次のとおり。

- ブラケットリンク `[ページ名]`、外部リンク `[URL タイトル]`、ハッシュタグ `#tag`
- 装飾 `[* 強調]` `[/ 斜体]` `[- 打ち消し]`、インラインコード、引用 `>`
- 行頭インデント（空白またはタブ）による箇条書き
- `code:ファイル名` によるコードブロック、`table:名前` によるテーブル
- 画像 URL の埋め込み、アイコン `[名前.icon]`（対象ページの最初の画像を表示する）
- 数式 `[$ ...]`（v1 ではコード表示。KaTeX はスコープ外）
- 同一インスタンス内の他プロジェクトへのリンク `/project/page`

### メディアの描画

本文中のメディア URL は、レンダラが拡張子とホストで分類して描画する。

- 画像（.png、.jpg、.jpeg、.gif、.webp、.svg の URL と Gyazo の URL）は `<img>` で表示する。
- 動画（.mp4、.webm）は `<video controls>`、音声（.mp3、.m4a、.ogg、.wav）は `<audio controls>` で表示する。
- YouTube などの動画サービス URL は iframe の埋め込みプレイヤーで表示できるようにする。ただし既定では埋め込まず、通常のリンクとして表示する（埋め込みは後述の CSP 許可リストと連動して有効化する）。
- 分類はレンダラ側の対応表で行い、新しい拡張子やホストの追加はこの対応表に閉じる。

添付ファイルのアップロードは画像に限らず、サイズ上限内であれば動画や音声も同じ仕組みで扱う。
容量の大きい動画は外部ホスティングの URL 埋め込みを推奨する。自前配信はバックアップ容量と帯域を消費するためである。

### 読み取り API

Cosense の読み取り API と同じパスと同じレスポンス形状を実装する。
Cosense の周辺ツール（エクスポータ、グラフ可視化、MCP サーバなど）はこの API に依存しているため、接続先を knot に向けるだけで動くことを互換性の柱とする。

```
GET /api/pages/:project                     ページ一覧（skip, limit, sort）
GET /api/pages/:project/:title              ページ本体（lines, links, relatedPages を含む）
GET /api/pages/:project/:title/text         プレーンテキスト
GET /api/pages/:project/:title/icon         ページアイコン（最初の画像）
GET /api/pages/:project/search/query?q=     全文検索
GET /api/pages/:project/search/titles       全ページのタイトルとリンク（リンクグラフ）
GET /api/code/:project/:title/:filename     コードブロック抽出
```

`relatedPages` には 1-hop リンク、2-hop リンク、逆リンクの有無を Cosense と同じ構造で含める。
`search/titles` はリンクグラフ可視化系ツールの主要な依存先であると同時に、knot 自身の 2-hop 計算とエディタの `[` 補完のデータ源を兼ねる。

互換性の約束は「動作保証する周辺ツールの列挙」で定義する。
代表的な周辺ツール（Cosense 向け MCP サーバとエクスポートツールから各 1 つ）を受け入れテストに採用し、CI で knot に向けて実行して動くことをもって互換とする。
フィールドの網羅は保証せず、受け入れテストのツールが参照するフィールドを優先する。

### インポートとエクスポート

- インポートは Cosense のエクスポート JSON を無加工で受け付ける。行が `{text, created, updated, userId, id}` のオブジェクト形式でも、文字列だけの簡易形式でも取り込める。行のタイムスタンプと userId は保持する。`users` 配列は表示専用ユーザー（password_hash なし、ログイン不可）として取り込む。
- タイトルが既存ページと衝突した場合の動作は、インポート時のオプションで「スキップ」「上書き」から選ぶ。既定はスキップ。
- インポートも内部的にはコミットとして記録する。すべての書き込みが commits に残る、という不変条件を保つためである。
- エクスポートは Cosense エクスポートと同じ構造の JSON（行メタデータ込み）を出す。`?format=import` を指定すると行を文字列配列にした簡易形式で出し、Cosense のインポート機能に直接渡せる形にする。
- 本文中の添付ファイル URL は knot 自身が配信する相対 URL であり、JSON 単体ではホストをまたいで可搬でない。`knot export --with-files` は files/ を同梱した zip を出力し、定期自動エクスポートではこれを既定とする。

## リンクとタグ

リンクは knot の中核機能であり、ページを組織する唯一の手段である。
散在しやすい定義をここに集約する。

- **リンク**：ブラケットリンク `[ページ名]` とハッシュタグ `#ページ名` は等価であり、どちらも title_lc で解決される（Cosense と同じ）。
- **タグ**：タグという独立した仕組みは持たない。タグとはハッシュタグ記法で書かれたリンクであり、タグページ（そのタイトルのページ）を開けば、逆リンク一覧としてタグ付けされたページが並ぶ。ページ実体のないタグも空リンクとして同様に機能する。
- **1-hop リンク**：このページのリンク先のうち、存在するページ。
- **逆リンク**：このページへリンクしているページ。閲覧画面の関連ページに常に表示する。
- **2-hop リンク**：このページのリンク先 L（空リンクを含む）を共有する他のページを、L ごとにグループ化したもの。
- **空リンク**：リンク先タイトルのページがまだ存在しないリンク。赤リンクとして描画し、クリックで新規作成に遷移する。書かれたが掘られていない場所を可視化する、という Cosense の設計思想を引き継ぐ。

これらはすべて、コミット適用時に AST から張り直す links テーブルへの SQL で導出する。
エディタの `[` と `#` の補完は `search/titles` と同じデータ源を使う。
リンクを張る摩擦の低さ（囲むだけ、補完が速い）が製品の生命線なので、補完はページ数万件の規模でも体感遅延なしを実装目標とする。

## 書き込み API

Cosense に公式の書き込み API は存在しないため、knot 独自の API は `/api/knot/` 名前空間に分離し、互換 API と混ざらないようにする。

```
POST   /api/knot/pages/:project/:title/commits   行操作のコミット（正準経路）
PUT    /api/knot/pages/:project/:title/text      全文置換
POST   /api/knot/pages/:project/:title/rename    タイトル変更（リンク元書き換えオプション付き）
DELETE /api/knot/pages/:project/:title           ページ削除
POST   /api/knot/projects/:project/import        Cosense JSON の取り込み
GET    /api/knot/projects/:project/export        Cosense 互換 JSON の書き出し
POST   /api/knot/files                           添付アップロード
POST   /api/knot/session                         ログイン
DELETE /api/knot/session                         ログアウト
```

- `PUT .../text` は行 ID を知らないクライアント向けの簡易経路である。`{baseVersion, text}` を受け取り、サーバが現行の行と LCS 差分を取って行操作に変換し、通常のコミットとして適用する。v2 の外部エディタ同期 CLI はこの経路を使う。LCS は内容ベースの差分なので、行の移動と編集が同時に起きた場合に行の同一性を誤ることがある。行メタデータ（created、userId）はベストエフォートであり、本文、リンク索引、検索、エクスポートの構造には影響しない。
- `rename` は「タイトル行の update」のコミット 1 件に帰着する。加えて、リンク元ページの `[旧タイトル]` を `[新タイトル]` に書き換えるかを `rewriteLinks: true` で指定でき、書き換えも各リンク元ページへの通常のコミットとして実行される。`rewriteLinks` の既定は false で、UI のダイアログで明示的に選んだ場合だけ書き換える。v1（SQLite）ではタイトル変更と全リンク元の書き換えを単一トランザクションで適用し、全部成功か全部失敗のどちらかにする。応答にはページごとの書き換え結果を含める。

## UI とエディタ

### 画面構成

```
GET /login                ログイン
GET /:project             ページ一覧（カードグリッド）
GET /:project/:title      ページ閲覧（SSR）
GET /:project/:title/edit 編集（CodeMirror）
```

- **ページ一覧**: カードグリッド。ピン留めが先頭、以降は更新順。カードにはタイトル、最初の画像、冒頭数行を表示する。ページングは「もっと見る」ボタンで行う。
- **ページ閲覧**: SSR で描画する。下部に関連ページ（1-hop、2-hop、このページへのリンク元）を表示する。存在しないページへのリンクは赤リンクとして描画し、クリックで新規作成に遷移する。
- **新規作成**: 赤リンクのクリック、または一覧の新規ボタンから編集画面を開く。ページの実体は最初のコミットで作られる。
- **ページ複製**: 閲覧画面の操作メニューから、新しいタイトルを指定して本文を複製した新規ページを作る。実体は「全行 insert の最初のコミット」であり、専用の仕組みを持たない。

### エディタ

CodeMirror 6 を使い、Scrapbox 記法のプレーンテキストを編集する。

- 記法のライブハイライト（リンク、装飾、コードブロックなどの装飾表示）
- `[` と `#` の入力で既存ページタイトルのオートコンプリート
- Tab / Shift-Tab によるインデント操作
- 画像のペーストとドロップでアップロードし、URL を挿入
- URL のペーストをリンク記法に変換する。テキストを選択して URL をペーストすると `[URL 選択テキスト]` になる。ただし、書き手が URL を生のまま置こうとしていると解釈できる文脈では発動しない。コードブロック内、インラインコード内、既存のブラケット `[ ]` の中がその例である。除外条件は、カーソル位置の構文情報を受け取って変換の可否を返す関数のリストとして実装し、後から追加できるようにする
- キーボードショートカット: Ctrl+I で自分のアイコン記法 `[ユーザー名.icon]` を挿入、Ctrl+B で選択範囲を `[* ]` で囲む
- 保存ボタンは置かない。編集停止から 500ms で自動コミットする。
- 自動保存は 3 つの状態を分離して管理する。**確認済みスナップショット**（サーバが保存を確認した version と行列）、**送信中コミット**（応答待ちの commitId と ops）、**未送信編集**（送信中コミットの作成後に発生した変更）である。送信中コミットはページごとに同時 1 件に制限し、成功応答を受けてから、未送信編集を新しい確認済みスナップショットとの差分として次のコミットにする。これにより、送信中に打った編集が「同期済み」と誤認されて消えることを防ぐ。409 のときは送信中コミットと未送信編集の両方をリベースに含める。
- タブクローズや画面遷移では `visibilitychange` / `pagehide` で未送信分を keepalive 付き fetch で送るが、これは保存完了を保証しない。確認が取れていないコミットはブラウザの永続ストレージにも書いておき、次回そのページを開いたときに同じ commitId で再送する。冪等性により二重適用は起きない。
- エディタはロード時に「行 ID 列付きのスナップショット」を受け取り、自動コミット時に現バッファとの LCS 行差分から行操作を生成して送る。行差分は core の純粋モジュールをバンドルに同梱し、`PUT .../text` のサーバ側処理とコードを共有する。CodeMirror の変更追跡で行 ID を逐次維持する方式は v1 の中で実装難度が突出するため採らず、リアルタイム化の段階で導入する。
- 409 応答時は「リベース」の節の 3-way で解決して再送する。

Cosense の「常に編集モード」（閲覧と編集の区別がない UI）は v1 では再現せず、閲覧画面と編集画面を分ける。
編集画面内の体験（保存操作が存在しない、記法が即座に装飾される）で Cosense の感覚を近似する。

### テロメア

各行の左端に、その行の更新の新しさを可視化するバー（Cosense の**テロメア**）を表示する。
可視化するのは 2 つの情報である。

- **行の新旧**：新しい行ほどバーを太く描画し、古い行ほど細らせる。
- **既読と未読**：自分が前回そのページを訪れた後に更新された行は、バーを青で描画する。判定は「前回表示した version」と「行を最後に変更したコミットの version」の比較で行い、閲覧時に page_visits を upsert する（「データモデル」の節を参照）。

テロメアにポインタを載せると相対時刻と編集者を表示し、クリックで詳細な時刻を表示する。

テロメアは**行 permalink** を兼ねる。
`/:project/:title#行ID` の URL でその行までスクロールして強調表示し、リンク記法 `[ページ名#行ID]` も同じ場所を指す（ページ名に `#` を含むタイトルと曖昧な場合は、完全一致するタイトルを優先して解決する）。

knot は各行を、独立した ID と更新メタデータ（updated、updated_version、user_id）を持つレコードとして保存しているため、テロメアの表示に必要な情報は全行にすでにある。
Cosense からインポートしたページでも、過去の編集時刻と行 ID がそのまま反映される。
エディタでは CodeMirror の gutter として同じ情報を表示する。

### 検索 UI

検索はインクリメンタル（打鍵ごとに結果を更新）とし、対象によって実装を分ける。

- **タイトル検索**：全タイトル（`search/titles` と同じデータ源）をクライアントに読み込み、fzf 相当の部分列マッチでスコアリングする。文字の間を飛ばすあいまい一致、語順の入れ替え、ひらがなとカタカナの同一視を含む。数万ページ規模でも打鍵ごとのマッチングは数 ms で収まり、サーバ往復が発生しない。タイトル一覧は初回に取得してキャッシュし、ETag で差し替える。エディタの `[` `#` 補完も同じマッチャを使う。
- **全文検索**：200ms 程度の debounce を挟んで `search/query` を打鍵ごとに呼ぶ。この規模の FTS5 は数 ms で応答するため、インクリメンタル表示に耐える。一致は部分文字列一致である（3 文字未満は LIKE フォールバック）。
- タイポ許容の全文検索（クエリを trigram に分解して OR 一致させ、一致した trigram 数で並べる方式）は、既存の索引のまま後から追加できる将来オプションとする。読み仮名によるあいまい一致（「とうきょう」で「東京」を当てる）は形態素解析の辞書が必要になるため、スコープ外とする。

## 認証とセキュリティ

v1 はログイン必須のクローズドな wiki である。ログインページと静的アセット以外の全ルートで認証を要求する。

- パスワードは Node 内蔵の scrypt でハッシュする。ユーザー作成は CLI（`knot user add`）で行い、Web からのサインアップは持たない。
- セッションはランダム 128 ビットの ID をクッキーに載せる。クッキー名は `connect.sid` とする。Cosense の周辺ツールの多くがこの名前でセッション ID を送る前提で作られており、名前を合わせるだけで「接続先の変更だけで動く」余地が広がるためである。属性は HttpOnly、Secure（http で動かすローカル開発時は除く）、SameSite=Lax。有効期限は 30 日のスライディング方式とする。
- v1 のアクセス制御は「ログインの有無」だけとする。ログインユーザーは全プロジェクトを読み書きできる。プロジェクト単位の権限は public 公開モードと同時に設計する。
- 書き込み API はカスタムヘッダ `X-Knot-Client` を必須にする。クロスオリジンのフォーム送信はカスタムヘッダを付けられないため、SameSite=Lax と合わせて CSRF を遮断できる。
- ログイン試行は IP とユーザー名の組でレートリミットする（インメモリ、10 回/10 分）。
- CSP は既定で self のみとする。img-src、media-src、frame-src は設定で外部ホストを許可できるようにする。Cosense からのインポートで Gyazo などの外部画像 URL が大量に入るため、img-src の既定には Gyazo を含める。frame-src（動画サービスの埋め込み）は既定で空とし、許可したホストだけ埋め込みプレイヤーが有効になる。
- 添付ファイルはサイズ上限（既定 10MB、設定可能）、content-type 検証、ランダム化した保存名で扱い、`X-Content-Type-Options: nosniff` を付けて配信する。sha256 が一致する既存ファイルがあれば再利用する。

### レンダリングと添付の安全化

利用者の入力から HTML を生成するため、保存型 XSS への対策をレンダラの仕様として定める。
CSP は被害を抑える緩和層であり、エスケープの代わりにはならない。

- レンダラはテキストノードと HTML 属性値を必ずエスケープする。
- リンクとメディアの URL は許可スキーム（http、https）だけを受け付ける。`javascript:` などの不許可スキームはリンク化せず平文で表示する。
- iframe は frame-src の許可ホストと照合してから生成する。許可外のホストでは iframe を生成しない。
- アップロードは申告された content-type を信用せず、対応できる形式についてはマジックバイトで内容を検査する。HTML と SVG はインライン表示せず `Content-Disposition: attachment` で配信し、knot のオリジンでスクリプトが動く経路を残さない。
- スクリプト要素、イベントハンドラ属性、`javascript:` URL を含む悪意ある入力を、レンダラのゴールデンテストに含める。

## 運用とバックアップ

- 起動は `knot serve --data ./data` の 1 コマンド。設定は環境変数またはフラグ（ポート、データディレクトリ、img-src 許可ホスト、アップロード上限）。Docker イメージも提供する。
- 必要リソースはメモリ 200MB 程度を想定する。自宅 PC + Cloudflare Tunnel なら 0 円、格安 VPS の最安プラン（月数百円）で月 1000 円以内の要件を満たす。
- バックアップは `knot backup` コマンドで行う。先に files/ をコピーし、その後に SQLite の backup API で knot.db のスナップショットを取る。v1 の添付ファイルは追加のみで削除がないため、この順序なら DB が参照するファイルがバックアップから欠けない。完了後に、DB が参照する全添付ファイルの存在を検証する。添付の削除機能を導入する時点でこの手順は見直す。
- それに加えて、Cosense 互換 JSON の定期自動エクスポートを設定できるようにする。DB ファイルとは独立した、データ形式に依存しない保険である。

## エラー処理

エラーは次の 3 系統に集約する。

- **409（競合）**: コミットの baseVersion 不一致、タイトルの一意制約違反。応答に最新状態を含め、クライアントが自動で取り込み直す。
- **401 / 403（認証と認可）**: 未ログインは HTML ルートではログイン画面へリダイレクト、API では 401 を返す。
- **404（不在）**: 存在しないページの閲覧 URL は、そのタイトルでの新規作成を促す画面を返す（赤リンクの遷移先と同じ）。API では 404 を返す。この解決は 1 箇所に集約し、将来の旧タイトルリダイレクトの差し込み点とする。

それ以外の失敗（パース不能な JSON、不正な行操作、上限超過のアップロードなど）は 400 系で個別に返し、5xx はログに集約する。
400 は再送しても直らないクライアント不正であり、409 と区別する。リベースと再送の対象は 409 だけである。

## テスト戦略

- **パーサとレンダラのゴールデンテスト**: 記法サンプル → HTML の期待値を固定し、レンダラの回帰を検出する。パーサを fork または乗り換える場合の受け入れ基準を兼ねる。
- **コミットエンジンのランダム編集テスト**: ランダムな行操作列を生成して適用し、lines の整合（ord の連続性、ID の一意性）と version の単調増加を検証する。同じコミット列の再適用が常に同じ行順に到達すること（決定性）、同一コミット内の連続挿入が入力順を保つこと、同じ行への並行挿入の期待順序も、ここで固定する。
- **リベースのプロパティテスト**: ランダムな並行編集の組に対して、リベース後の適用が収束すること（全クライアントがサーバの最終状態に到達すること）、自分が触っていない行への他者の編集を上書きしないこと、挿入先の行が削除されていても挿入内容を失わないことを検証する。同一行を更新した競合（受理順の後勝ち）と、別々の行への独立した更新は、別のケースとしてテストする。
- **冪等性のテスト**: 同じ commitId と同じ内容の再送が version を二度増やさず最初の version を返すこと、同じ commitId で異なる内容が 400 で拒否されることを検証する。
- **バックアップの復元テスト**: `knot backup` の出力から新しいデータディレクトリへ復元し、サーバが起動して DB の参照する添付ファイルが欠けていないことを検証する。
- **実データの round-trip テスト**: 実際の Cosense エクスポート JSON をインポートし、エクスポートして、意味的な同値性（ページ数、行テキスト、タイムスタンプ、userId の保存）を確認する。`PUT .../text` 経由で編集したページの行メタデータは、ベストエフォートのため厳密一致の対象から外す。
- **周辺ツールの受け入れテスト**: 互換性の定義として採用した周辺ツールを、CI で knot に向けて実行する。
- **API の E2E**: Hono の `app.request` でルーティングから storage までを通しでテストする。
- **エディタのスモークテスト**: Playwright で「開く、編集する、自動保存される、再読み込みで内容が残る」の 1 本だけを維持する。

core と render は純粋モジュールなので、テストの大半は DB もサーバも立てずに実行できる。

## 将来拡張の設計上の対応

### リアルタイム共同編集

WebSocket エンドポイントを追加し、適用済みコミットをページ購読者へ配信する。
エディタは受信した ops を逐次適用し、自分の未確定編集を v1 で仕様化した rebase 関数でリベースする。
この段階で、エディタに行 ID の逐次追跡（v1 では見送った方式）を導入する。
正準形式（行操作 + version + commits ログ）は v1 から存在するため、DB スキーマ、API、レンダラ、認証は変更しない。
変更されるのはエディタの保存層と、WS ゲートウェイの追加に限られる。
行内の文字単位の同時編集が必要になった場合に限り、そのときに Yjs の導入を検討する（CodeMirror 6 には Yjs バインディングがあり、エディタ部品は流用できる）。

### 旧タイトルからのリダイレクト

存在しないタイトルへのアクセスを、タイトル変更前にその名を持っていたページへリダイレクトする機能。

素朴に「タイトル変更の履歴」を引くだけでは成立しないことが、Cosense の開発者によって指摘されている。
タイトル行の編集は逐次保存されるため、「カレー」を「curry」へ変える途中の「カレ」「カ」「c」「cu」のような一時タイトルが履歴に残り、「カ」へのアクセスが curry へリダイレクトされてしまうためである（Cosense はこの理由でアクセス履歴方式を採っている）。

knot の title_history は有効期間（started、ended）を記録しているので、「一定時間以上そのページのタイトルであり続けたタイトル」だけをリダイレクト対象にする方針を第一候補とする。
編集途中の一時タイトルは数秒しか存続しないため、この条件で除外できる。
精度が足りない場合の代替として、Cosense と同じアクセス履歴方式へ切り替えられる。テロメアのために v1 から記録する page_visits と title_history を突き合わせれば、「そのタイトルであった期間に実際に閲覧されたことのあるタイトル」だけをリダイレクト対象にできる。
どちらの方式でも、v1 の 404 ハンドラ（新規作成を促す画面）が単一の差し込み点になる。

### 外部エディタ同期 CLI（v2）

`PUT .../text` が同期の書き込み経路、`GET .../text` と一覧 API が読み取り経路になる。
CLI は「1 ページ = 1 テキストファイル」でローカルディレクトリに書き出し、ファイルの変更を baseVersion 付きで push する。
409 が返った場合の解決（ローカル優先、リモート優先、マージ）は CLI 側の設計課題として v2 で扱う。
書き出したディレクトリはそのまま git で管理でき、「clone して import で復元」というファイルベースの持ち出し経路を兼ねる。ただしテキストファイルは行メタデータ（行ごとの created、userId）を持たないため、この経路での復元はベストエフォートになる。完全な復元は Cosense 互換 JSON のエクスポートが担う。

### Cloudflare Workers / D1

server は Hono なのでハンドラはそのまま動く。
storage の SQLite 実装を D1 実装に差し替え、添付ファイルを R2 に置く実装を追加する。
D1 では複数ページの原子的更新を前提にできないため、rename のリンク書き換えは「冪等なジョブとして記録し、失敗したページを再実行できる」方式に置き換える。
node:sqlite と scrypt への依存は storage と auth のモジュール内に閉じ込めておく。
FTS5 trigram が D1 で使えない場合に備え、検索はストレージ interface の 1 メソッドとして抽象化しておく。

## 技術選定の根拠

検証済みの事実:

- @progfay/scrapbox-parser 10.1.1（MIT）が npm に存在し、Scrapbox 記法のパースを提供する（2026-07-10 確認）。
- Node v24.18.0 の node:sqlite（SQLite 3.53.1）で FTS5 の trigram トークナイザが動作し、日本語の部分一致検索が成立する（同日、ローカルで動作確認）。

選定理由:

- **TypeScript**: パーサ資産を直接使える唯一の言語であり、サーバとエディタを単一言語で書ける。Workers への移行路も保てる。
- **Hono**: Node、Bun、Deno、Workers で同一コードが動くことを設計目標としたフレームワークであり、「v1 は Node、将来 Workers」の方針に一致する。
- **node:sqlite + scrypt**: ランタイム内蔵機能を使うことで、ネイティブ依存のビルド問題と依存パッケージの寿命リスクを避ける。node:sqlite の API がまだ安定途上である点は残るリスクだが、依存は storage 内に閉じており、問題が出た場合は better-sqlite3 に差し替える。
- **@progfay/scrapbox-parser**: 実質単独メンテのパッケージだが、依存ゼロの純粋なパーサで対象記法も安定しているため、バージョン固定とゴールデンテストを受け入れ基準として fork の維持まで含めて現実的と判断した。
- **CodeMirror 6**: 長期メンテナンスの実績があるエディタ基盤で、記法ハイライト、補完、変更追跡（行 ID の維持に使う）を備える。
- **SSR 主体で SPA を持たない**: 依存を減らし、ビルドの複雑さをエディタのバンドル 1 点に絞るため。バンドラは esbuild を使う。
