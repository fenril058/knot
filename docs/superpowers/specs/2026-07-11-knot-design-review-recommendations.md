# knot 設計書への修正提言

対象: `docs/superpowers/specs/2026-07-10-knot-design.md`

作成日: 2026-07-11

## 目的

この文書は、knot v1 の実装前に設計書へ反映すべき修正を示す。

優先度「高」の提言は、競合時のデータ喪失、操作結果の非決定性、保存失敗、保存型クロスサイトスクリプティングにつながるため、実装開始前に仕様を確定する。

## 優先度の定義

- **高**：実装の正しさ、データ保全、セキュリティに影響するため、実装開始前に設計書を修正する。
- **中**：v1 の実装中に仕様判断が必要になるため、該当機能へ着手する前に設計書を修正する。
- **低**：仕様の理解や保守性を改善するため、設計書の次回改訂時に修正する。

## リベースに必要な入力

優先度: 高

設計書では、409 応答が最新のページ状態を返す一方、リベース関数は `missedCommits` を入力に要求している。
この二つの仕様は一致していない。

最新のページ状態だけでは、並行編集で削除された挿入先の旧位置や、最後の同期後に適用された操作列を復元できない。

次のどちらかに統一する。

1. 409 応答に、`baseVersion` より後のコミット列を含める。
2. リベース関数を `rebase(baseSnapshot, localBuffer, latestSnapshot)` とし、コミット列を必要としない 3-way merge として定義する。

v1 では、409 応答の大きさとサーバー実装を単純にできる第 2 案を推奨する。
削除された挿入先の旧位置は `baseSnapshot` から求める。

受け入れ条件:

- 409 応答だけで、クライアントが再送する操作列を計算できる。
- 他の利用者だけが変更した行を、ローカルの古い内容で上書きしない。
- 挿入先の行が削除された場合にも、挿入内容を失わない。

## 同じ位置へ挿入された行の順序

優先度: 高

現在の insert 操作は `after` だけで挿入位置を表す。
複数の操作が同じ行の後ろへ挿入した場合の順序は定義されていない。

「指定行の直後へ挿入する」だけでは、操作の到着順によって行順が反転する可能性がある。
同一コミット内、並行コミット間、ページ先頭への挿入について、同じ規則で順序を決定する必要がある。

行順を決定するため、次の情報を比較する規則を定義する。

- サーバーが確定したコミットの version
- コミット内の操作位置
- 必要な場合の行 ID

行 ID だけで並べると、利用者が入力した順序と一致しない可能性がある。
同一コミット内では操作位置を優先し、異なるコミット間ではサーバーが確定した version を優先する方法を推奨する。

受け入れ条件:

- 同じ操作列を適用すると、常に同じ行順になる。
- 一つのコミットで連続して挿入した行は、利用者が入力した順序を保つ。
- 同じ基準行への並行挿入について、期待する行順をテストで固定できる。

## 同一行を更新した競合の解決

優先度: 高

設計書の「後勝ち」は、何をもって後とするかが定義されていない。
クライアントの編集時刻、最初の送信時刻、リベース後の再送順では結果が異なる。

v1 のサーバー直列化方式では、サーバーが受理したコミット順を基準にする。
409 を受けたクライアントがローカル更新をリベースして再送した場合、その再送コミットが同一行の先行更新を置き換える、と明記する。

テスト戦略で使う「収束」は、全クライアントがサーバーの最終状態へ到達することとして定義する。
競合した双方の変更を保存することまでは意味しない。

受け入れ条件:

- 同一行を更新した二つのコミットについて、どちらの内容が残るかをサーバーの受理順から決定できる。
- すべてのクライアントが、最終的にサーバーと同じページ状態を表示する。
- 同一行の競合と、別の行への独立した更新を別々にテストする。

## 自動保存の状態管理

優先度: 高

自動保存のリクエスト送信中にも、利用者は編集を続けられる。
確認済みの状態、送信中の操作、未送信の編集を分離しなければ、応答到着後に新しい編集を同期済みとして扱う可能性がある。

エディタは、次の状態を別々に保持する。

- **確認済みスナップショット**：サーバーが保存済みであると確認できた version と行列。
- **送信中コミット**：応答を待っている `commitId` と操作列。
- **未送信編集**：送信中コミットの作成後に発生した変更。

一つのページについて、送信中コミットは一件に制限することを推奨する。
成功応答を受けた後、未送信編集を新しい確認済みスナップショットとの差分として送信する。
409 応答時には、送信中コミットと未送信編集の両方を失わないようにリベースする。

`pagehide` と keepalive 付き fetch は、サーバーによる保存完了を保証しない。
未確認コミットをブラウザーの永続ストレージへ保存し、次回表示時に同じ `commitId` で再送する。

受け入れ条件:

- 保存要求の送信中に追加入力しても、追加分が消えない。
- 応答を受け取る前にタブを閉じても、次回表示時に未確認コミットを再送できる。
- 同じコミットを再送しても version が二度増えない。
- 409 処理中に発生した編集も保存される。

## コミットの冪等性を支えるスキーマ

優先度: 高

設計書は、適用済み `commitId` の同一リクエストを成功として扱う。
しかし、現在の `commits` の概略には、同一性を検証するための `baseVersion` と制約がない。

`commits` に次の情報と制約を追加する。

- `base_version`
- 正規化したリクエスト内容のハッシュ
- `UNIQUE(id)`
- `UNIQUE(page_id, version)`

JSON の空白やプロパティ順まで含む「バイト同一」ではなく、正規化した `{pageId, baseVersion, ops}` が同一であることを判定する。
同じ `commitId` で異なる内容を受け取った場合は 409 ではなく 400 を返す。

受け入れ条件:

- 同じ `commitId` と同じ内容の再送は、最初に適用した version を返す。
- 同じ `commitId` と異なる内容の要求は拒否する。
- プロセス再起動後にも冪等性が保たれる。

## レンダリングと添付ファイルの安全性

優先度: 高

利用者の入力を HTML に変換し、外部 URL と添付ファイルを配信するため、保存型クロスサイトスクリプティングへの対策をレンダラーの仕様として定める。
CSP は被害を抑える対策であり、HTML の安全化を置き換えない。

次の規則を追加する。

- テキストノードと HTML 属性値を必ずエスケープする。
- リンク、画像、動画、音声の URL は許可したスキームだけを受け付ける。
- iframe の URL は、設定された許可ホストと照合する。
- アップロード時に申告された Content-Type だけを信用せず、対応できる形式では内容も検査する。
- HTML と SVG を許可する場合は、インライン表示せずダウンロードとして配信する。
- 添付ファイルへ `X-Content-Type-Options: nosniff` と適切な `Content-Disposition` を付ける。

受け入れ条件:

- スクリプト要素、イベントハンドラー属性、`javascript:` URL を含む入力が実行されない。
- 許可していないホストの iframe を生成しない。
- HTML または SVG の添付ファイルを開いても、knot のオリジンでスクリプトが動作しない。
- 悪意ある入力をレンダラーのゴールデンテストへ追加する。

## ページ URL とタイトルの表現

優先度: 中

`/:project/:title` というルートでは、タイトルに `/`、`?`、`#`、`%` が含まれる場合の解決規則が必要になる。
特に URL のフラグメントはサーバーへ送信されないため、サーバーはタイトル中の `#` と行 permalink の区切りを判定できない。

タイトルを URL に埋め込むときの percent-encoding と復号を一か所に実装し、往復可能性をテストする。
行 permalink のフラグメントはクライアント側で解釈する。

経路の曖昧さを避けるため、ページ URL を `/:project/p/:encodedTitle` のような専用の名前空間へ置く案を推奨する。
タイトルの表現範囲を制限する場合は、Cosense から取り込めないタイトルが生じるため、その制限と変換規則をインポート仕様へ明記する。

受け入れ条件:

- `/`、`?`、`#`、`%`、空白、アンダースコアを含むタイトルを作成し、同じタイトルとして取得できる。
- 他プロジェクトへのリンクと通常のページ URL が衝突しない。
- 行 permalink を開くと、指定した行だけを強調する。

## タイトル変更に伴うリンク書き換え

優先度: 中

`rewriteLinks: true` は複数ページへコミットするため、途中の競合や失敗によって一部のリンクだけが書き換わる可能性がある。

SQLite 実装では、タイトル変更とリンク元ページへのコミットを一つのトランザクションで適用する案が単純である。
ただし、将来の D1 実装では複数ページの原子的な更新を前提にできない。

将来のストレージ移行を優先する場合は、リンク書き換えを冪等なジョブとして記録し、進捗と失敗したページを再実行できるようにする。
いずれの方式でも、競合時の全体的な結果を API 応答で確認できるようにする。

Cosense に近いリンクの履歴を残すため、`rewriteLinks` の既定値は `false` を推奨する。

受け入れ条件:

- リンク元ページの一つで競合した場合の結果が仕様から決まる。
- 処理を再実行しても、同じリンクを重複して変更しない。
- 部分成功を許す場合は、失敗したページを取得して再実行できる。

## バックアップ時の添付ファイル整合性

優先度: 中

SQLite のスナップショット取得と `files/` のコピーを別々に行うと、その間のアップロードによって DB とファイル集合の時点がずれる。

v1 では、バックアップ中だけ添付ファイルの登録と削除を停止する方法を推奨する。
バックアップ完了後に、DB が参照するすべての添付ファイルがバックアップ内に存在することを検証する。

復元手順と復元テストもテスト戦略へ追加する。

受け入れ条件:

- 復元後、DB が参照する添付ファイルが欠けていない。
- バックアップ中にアップロード要求が来た場合の待機または失敗が仕様化されている。
- 自動テストでバックアップから新しいデータディレクトリへ復元できる。

## 未読判定に使う version

優先度: 中

すべての時刻を Unix 秒で保存すると、行更新とページ閲覧が同じ秒に起きた場合の未読判定が曖昧になる。

`page_visits` に `last_seen_version` を追加し、未読判定にはページの version を使う。
Cosense 互換 API と表示に使う時刻は、従来どおり Unix 秒で保持する。

ページを表示するときは、レスポンスに含めた version を `last_seen_version` として保存する。
行がどの version で最後に更新されたかを判定するため、`lines` に `updated_version` を持たせる。

受け入れ条件:

- 閲覧と更新が同じ Unix 秒に発生しても、未読かどうかを一意に判定できる。
- ページ表示中に新しいコミットが適用された場合、そのコミットによる変更を未読として扱う。

## 用語と記述の修正

優先度: 低

「正準形式」は初出で定義されているため、そのまま使用できる。

「文脈述語」は一般に定着したエディタ設計の用語ではないため、通常の説明へ置き換える。

修正例:

> カーソル位置がコードブロック、インラインコード、既存のブラケット記法の内側にある場合は、URL の自動変換を行わない。
> 除外条件は、カーソル位置の構文情報を受け取る関数として追加できるようにする。

「行が第一級」は指す性質が曖昧なため、データ構造を直接説明する。

修正例:

> knot は各行を、独立した ID と更新メタデータを持つレコードとして保存するため、テロメアの表示に必要な情報を全行から取得できる。

## 設計書へ先に反映する項目

実装開始前に、次の順序で設計書を更新する。

1. 409 応答とリベース関数の入力を一致させる。
2. 並行 insert と同一行更新の決定規則を定義する。
3. 自動保存の送信中、未送信、再送の状態を定義する。
4. `commitId` の一意性と要求同一性をスキーマへ反映する。
5. HTML、URL、iframe、添付ファイルの安全化規則を追加する。
6. URL、リンク書き換え、バックアップ、未読判定の仕様を確定する。

上記を反映した後、テスト戦略の各項目を具体的な受け入れ条件へ対応付ける。
