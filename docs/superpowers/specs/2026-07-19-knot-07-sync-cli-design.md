# knot 07: 外部エディタ同期 CLI（knot sync）設計書

作成日: 2026-07-19
状態: 承認済み

v1 設計書（`2026-07-10-knot-design.md`）が「外部エディタ同期 CLI（v2）」として予約した機能を実装する。
設計は Codex によるコードレビュー（二往復）を経て、現行実装の API 仕様と突き合わせて確定した。

## 目的

Emacs や Vim などの外部エディタで knot のページを編集できるようにする。
「1 ページ = 1 テキストファイル」でローカルディレクトリに書き出し、手動の pull / push でサーバと同期する。
書き出したディレクトリはそのまま git で管理でき、ファイルベースの持ち出し経路を兼ねる。

この形式は行メタデータ（行ごとの created、userId）を持たないベストエフォートの経路である。
完全な復元は既存の Cosense 互換 JSON エクスポートが担う。

## スコープ

実装するもの:

- `knot sync` サブコマンド群（init / pull / push / status）
- サーバ側の変更 1 点: ページ一覧 API レスポンスへの knot 拡張フィールド `version` の追加

実装しないもの（将来拡張）:

- watch による常駐同期デーモン
- 3-way 自動マージ（共通祖先の保存が必要になった時点で導入を検討する）
- ローカルでの削除・リネームの push 伝播
- 複数プロジェクトの一括同期（1 ディレクトリ = 1 プロジェクト）
- 添付ファイルの同期（テキスト中の URL 参照のままとする）

## コマンド構成

既存 CLI に `knot sync` サブコマンド群を追加する。
HTTP クライアントとして動き、サーバと別マシンで実行できる。
既存コマンドと異なり `--data` を取らない。

- `knot sync init <dir> --url <base-url> --project <name>` — 同期ディレクトリを初期化する
- `knot sync pull` — リモートの変更をローカルファイルへ反映する
- `knot sync push` — ローカルの編集をリモートへ送信する
- `knot sync status` — ローカル変更と競合の一覧を表示する（既定はネットワークアクセスなし。`--remote` でリモート差分も取得する）

## 認証

実装済みの API トークン（`knot_` プレフィックス）を使う。

- リクエストヘッダは `x-personal-access-token`（現行サーバは `Authorization: Bearer` を見ない）。
- 書き込み（POST / PUT / DELETE の `/api/knot/*`）には `X-Knot-Client: knot-sync` も送る。
- トークンは環境変数 `KNOT_TOKEN` を優先し、なければ `.knot/token` ファイル（mode 600）から読む。
- `init` は `.knot/` を gitignore へ追記するよう案内する（トークンと state を git 管理に入れない）。

`config.json` の URL は正規化して保存する（末尾スラッシュの除去、userinfo 埋め込みの拒否）。

## ディレクトリレイアウト

```
<dir>/
  カレーの作り方.txt      ← 1 ページ = 1 ファイル（1 行目 = タイトル行）
  .knot/
    config.json           ← url / project
    state.json            ← 同期状態（後述）
    token                 ← 任意（KNOT_TOKEN が優先）
    conflicts/<pageId>/remote.txt  ← 競合時のリモート本文の隔離先
```

### ファイル名規約

ファイル名はタイトル由来とし、人間の可読性を優先する。

- タイトルをそのまま使い、OS で使えない文字（`/ \ : * ? " < > |`）、`%` 自体、先頭のピリオド、末尾の空白・ピリオド、Windows 予約名（CON、PRN、AUX、NUL、COM1 など）のみ percent-encode でエスケープする。
- エスケープは単射（逆変換可能）とし、core にユニットテストつきの純関数として置く。
- 拡張子は `.txt`。

相異なるページはサーバが title_lc（NFC 正規化 + 小文字化 + 空白→`_`）で一意性を強制するため、原理的にはファイル名が衝突しない。
ただし FS のケースフォールディングが Unicode の小文字化と一致しない例外（ギリシャ語 `σ`/`ς`、トルコ語 `İ`/`ı` など）が残る。
このため pull 時に実 FS 上での衝突を検出し、衝突した場合のみ接尾辞（`~2` など）で回避する。
pageId → 実ファイル名の対応は常に state.json に記録し、ファイル名からの逆算に依存しない。

### 本文の正準形

ハッシュ計算と比較は次の正準形で行う。

- エンコーディングは UTF-8、BOM なし。
- 改行は LF。push 前に CRLF を LF へ正規化する。
- 末尾改行なしの全行結合（サーバの `GET .../text` の形と一致させる）。
- ファイル書き出し時は POSIX 慣習に合わせ末尾に LF を 1 つ付け、読み込み時に 1 つだけ取り除いてから比較する。

## state.json

同期ディレクトリの `.knot/state.json` に、ページごとの最終同期状態を記録する。

```json
{
  "pages": {
    "<pageId>": {
      "title": "カレーの作り方",
      "filename": "カレーの作り方.txt",
      "version": 12,
      "contentHash": "sha256:..."
    }
  }
}
```

- `version` と `contentHash` は「最後に同期した時点」の値。
- ローカル編集の検出はファイル内容の正準形ハッシュと `contentHash` の比較で行う。
- リモート更新の検出は一覧 API の `version` と state の `version` の比較で行う。
- 書き込みはアトミック（tmp + rename）。
- push / pull ともページ 1 件の成功ごとに state を更新し、中断しても次回実行で収束する冪等設計とする。

## pull の意味論（リモートが正）

手順:

1. 一覧 API（`GET /api/pages/:project`、`sort=title`）をページングで最後まで取得する。
2. 取得の完全性を検証する: 全リクエスト成功、pageId の非重複、count と取得件数の一致。満たさない場合は削除判定を行わない。
3. state の `version` と異なるページのみ、タイトルで詳細 API（`GET /api/pages/:project/:title`）を取得する。
4. **詳細応答の `id` が一覧の `id` と一致することを必ず検証する。**不一致・404・通信失敗の場合はそのページをスキップして報告し、state もファイルも変更しない（削除済みページのタイトルは再利用可能なため、タイトル解決が別ページを返しうる）。

判定表（ページ ID をキーとする）:

| ローカル | リモート | 動作 |
|---|---|---|
| 未変更 | 更新あり | ファイルを上書きし、state を更新する |
| 変更あり | 更新なし | 何もしない（push 待ち） |
| 変更あり | 更新あり | 競合。ファイルは触らず `.knot/conflicts/<pageId>/remote.txt` にリモート本文を書き出して報告する |
| 未変更 | 削除された | ローカルファイルを削除し、state から除く |
| 変更あり | 削除された | ファイルは残して報告する |
| — | リネームされた | ID で追跡し、旧ファイル削除 + 新名で書き出す。ローカル変更ありなら競合として扱う |

ローカルでファイルを削除した場合、削除は伝播しないため次回 pull で復元される（仕様として明記する）。

## push の意味論（更新と新規作成のみ）

- 正準形ハッシュが state と異なるファイルを対象に、`PUT /api/knot/pages/:project/:title/text` へ `baseVersion` = state の `version` を添えて送信する。
- state に無い新規ファイルは `baseVersion: 0` で送信し、新規ページとして作成する（サーバ実装済みの経路）。URL のタイトルにはファイル 1 行目を使う（サーバが 1 行目と URL タイトルの titleLc 一致を要求するため）。ファイル名から復元したタイトルと 1 行目が titleLc 単位で食い違う場合は送信せず報告する。作成後は詳細 GET を再取得して pageId を得て state に記録する。
- push 前に、新規ファイル群と既存ページの titleLc 重複を検査し、重複があればそのファイルをスキップして報告する。
- **リネーム検査**: ファイル 1 行目のタイトルが、state に保存した同期時タイトルと titleLc 単位で一致しない場合、リネーム企図としてエラー報告し送信しない（サーバは既存ページのタイトル行変更をリネームとして受理してしまうため、CLI 側の検査が防波堤になる）。
- **409（リモートが先行）**: 該当ページをスキップして続行し、最後にまとめて報告する。`--force` は最新 version を取得し直して 1 回だけ上書きを再試行する（force-with-lease 相当の意味論。無制限リトライはしない）。
- **応答喪失**: PUT は冪等キーを持たないため、結果不明時に再送しない。詳細 GET を取得し、本文一致で成功を判定してから state を更新する。

## サーバ側の変更

ページ一覧 API のレスポンス整形（`summaryToJson`）に knot 拡張として `version` を追加する。
ストレージ層は内部で `version` を保持済みのため、変更は整形関数 1 箇所に閉じる。
受け入れテスト対象の cosense-cli と scrapbox-cosense-mcp は未知フィールドを許容することをコードで確認済み。
変更後に `test/server/read-list.test.ts` と受け入れテスト 2 本の回帰を確認する。

## CLI 実装の配置

- 同期コードは `src/cli/sync/` に分離する（client / state / filenames / decisions / commands）。
- pull / push の判定ロジック（判定表）は I/O から分離した純関数にする。
- 既存 dispatcher（`src/cli/main.ts`）は全コマンドに `--data` を要求する構造のため、`--data` 必須判定をローカル管理コマンド側へ移す再構成を行う。

## エラー処理

- push / pull とも 1 ページずつ処理し、失敗はそのページのみスキップして最後にまとめて報告する（部分成功を許す）。
- exit code: 0 = 全成功、1 = 競合または部分失敗、2 = 設定・認証・接続の失敗。

## テスト戦略

- core / 純関数: ファイル名エスケープの round-trip、正準形変換（CRLF、末尾改行、BOM）、pull / push 判定表のユニットテスト。
- 統合テスト: 実サーバをテスト内で起動し、init → pull → 編集 → push → 競合 → 409 → `--force` のシナリオを検証する。
- 異常系: 一覧取得中の更新（件数不一致）、詳細 GET の id 不一致、PUT 応答喪失後の再実行、リモートのリネーム・削除、CRLF 入力、新規ファイルの titleLc 重複。
- docs: README と ops.md に「git 管理と組み合わせた持ち出し」の節を追加する。
